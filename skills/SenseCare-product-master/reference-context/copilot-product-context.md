# 大医医助 Copilot 产品上下文基线

## 1. 文档定位
1. 本文档是大医医助 Copilot 当前产品上下文基线，用于配合后续迭代 PRD 使用。
2. 本文档为研发人员和代码生成 AI 提供稳定的产品背景、系统边界和术语口径。
3. 本文档不是某一次迭代的需求说明，不替代当期 PRD。当期 PRD 应只描述本期要新增、修改、删除或明确不影响的内容。
4. 本文档中的概念均按当前基线理解；当期需求模块如需改变基线定义，必须在“模块上下文说明”的“基线差异”中明确说明。

## 2. 大医医助是什么
### 2.1 基线定义
1. 大医医助是面向医疗机构的桌面版医疗 AI 工作台。
2. 产品目标模式为 2B，产品类型为应用平台型。
3. 产品依托大医医疗垂类模型，以及 BOTS 平台的提示工程、知识库、工作流、插件等工程化能力，为医院内不同角色提供智能体服务。
4. 主体部署方式为医疗机构私有化部署，不默认包含公网接入或面向公网发布服务。

### 2.2 目标用户
1. 普通用户：在 PC 端使用大医医助的临床、科研、医技、护理及日常办公用户。
2. 机构管理员：在管理后台配置机构、用户、智能体、系统参数等内容的用户。
3. 超级管理员：具备全部后端管理权限和数据权限的管理用户。

### 2.3 核心场景
1. 门诊辅助：诊断建议、治疗方案推荐、病历记录辅助、医学知识查询等。
2. 住院辅助：查房、治疗方案调整、护理指导、病历更新、病情分析等。
3. 科研辅助：文献检索与整理、课题申报、实验设计、数据分析、论文撰写等。
4. 暂不涉及：医疗手术直接操作、大型医疗设备操作维护、医保理赔、医疗纠纷处理等高风险或跨法律保险领域场景。

## 3. Copilot 在大医医助中的位置
### 3.1 基线定义
1. “大医医助 Dayi-Copilot”是桌面端客户端工作台，包括普通侧边栏、最大化吸附侧边栏、悬浮气泡、首页、对话页、应用面板、历史记录、智能划词、智能截图、用户设置等能力。
2. 大医医助后台管理模块承担智能体应用管理平台的角色，用于承接 BOTS 发布到 Copilot 的智能体，并在机构内进行安装、配置、启停、权限分配和调用。
3. 病历生成等智能体应用基于 Copilot 应用平台建设，Copilot 是智能体应用的承载和调用入口。

### 3.2 不应误解的边界
1. Copilot 不是单个智能体。
2. Copilot 不等同于 BOTS 智能体开发平台。
3. Copilot 不应直接替代 HIS、EMR、LIS、RIS、手麻、护理等院内业务系统；它通过接口获取上下文数据，辅助智能体完成问答、生成、摘要、处理等任务。
4. Copilot 的页面公共能力、Qt 客户端底座能力、具体智能体应用能力应区分描述，避免把页面或应用能力误写成底座能力。

## 4. 既有功能结构
### 4.1 管理后台
1. 机构管理：创建、编辑和管理机构及机构下属部门。
2. 用户管理：创建、编辑、删除用户，管理用户所属机构部门、账号状态和权限。
3. 智能体管理：对接智能体开发平台，引入已发布的智能体，并对机构、部门或用户进行配置与分配。
4. 系统配置管理：维护系统级通用参数。
5. 智能体安装与机构配置：支持承接 BOTS 发布到大医医助 Copilot 的智能体，通过 Copilot 后台应用市场安装到机构，支持安装范围、机构配置、权限分配、启停和删除等管理能力。

### 4.2 Copilot 客户端
1. 登录页：账号密码登录、记住账号、自动登录等。
2. 普通侧边栏和最大化吸附侧边栏：最大化、最小化、应用面板、历史记录、回到首页、拖拽移动、垂直放缩、Logo、标题、底部声明等。
3. 首页：欢迎词、多功能输入框、智能体列表、文件拖拽热区。
4. 对话页：提问区、回答区、推理过程展示、多功能输入框、上传文件、截图提问、模型模式与思考开关等。
5. 智能体广场：展示当前用户可使用的智能体，支持查看、启动、收藏。
6. 历史对话：按时间查看、改名、置顶、删除历史对话。
7. 智能划词工具：划选文字后进行翻译、总结、解释、问问大医等。
8. 智能截图工具：截图后进行文字提取、翻译、总结、解释、引入对话等。
9. 悬浮气泡：最小化后的快捷入口，支持打开大医快问、还原窗口、拖拽、右键菜单等。
10. 用户设置：账户设置、通用设置、AI 工具设置、反馈与关于。

## 5. “Common / Qt 客户端底座 / 应用”的推荐协作口径
### 5.1 Common 公共能力
1. 定义：Copilot 页面、管理后台、多个功能、多个智能体或多个页面共同复用的业务与前端能力。
2. 包含：
   - 前端配置、登录、用户基础信息、账号状态。
   - 首页、会话历史、智能体广场、智能体切换。
   - 患者列表、患者关联、通用模式、诊疗模式。
   - 问答展示、流式输出、推理过程展示等回答呈现能力。
   - 管理后台中被多个业务复用的机构、用户、权限、系统配置能力。

### 5.2 Qt 客户端底座
1. 定义：Copilot 底座指 Qt 包客户端底座，是承载 Copilot Web 页面的前端运行容器。
2. 包含：
   - Qt 客户端包、窗口容器、侧边栏/最大化吸附栏/悬浮气泡等外壳形态。
   - 内置浏览器容器，负责加载和展示 Copilot Web 页面内容。
   - 客户端与 Web 页面之间的消息通信、事件桥接和能力调用。
   - 客户端对本地能力或院内接口的转发、代理、唤起、回调。
   - 客户端级配置读取、窗口状态保持、本机侧运行环境适配。

### 5.3 智能体应用
1. 定义：在 Copilot 中被用户选择、打开和使用的具体智能能力。
2. 包含：自由对话、AI 划词、AI 截图、通用翻译、通用总结、通用解释、指南解读、论文解读、科研问答、专病问答、病历生成等。
3. 智能体应用标准类型包括：
   - 助理型智能体（曾用名：原生智能体）：病历生成、专病问答等产品内置或定制类应用。
   - 问答型智能体（曾用名：自建智能体）：院内客户在 BOTS 开发并发布上线的智能体，主要是 ChatBot 类。
   - 工具型智能体（曾用名：智能工具）：自由对话、AI 划词、AI 拍照/截图上的翻译、总结、解释等工具类功能。

## 6. 智能体应用类型
### 6.1 工具型智能体（曾用名：智能工具）
1. 定义：面向轻量任务的一类智能体应用，用于完成自由问答、翻译、总结、解释、文字提取等任务。
2. 包含：自由对话、AI 划词、AI 截图、通用翻译、通用总结、通用解释、文字提取等。

### 6.2 助理型智能体（曾用名：原生智能体）
1. 定义：大医医助产品中面向特定场景提供的定制类智能体应用。
2. 包含：科研问答、文献解析、病历生成、专病问答等。

### 6.3 问答型智能体（曾用名：自建智能体）
1. 定义：院内客户在 BOTS 开发上线并发布到 Copilot 的智能体，主要是 ChatBot。
2. 接入方式：通过 BOTS 的“发布到大医医助 Copilot”渠道发布，再由 Copilot 后台应用市场安装到机构。
3. 包含：院内自建问答智能体、院内自建业务助手、院内自建流程型 ChatBot 等。

## 8. BOTS 与 Copilot 的分工原则
### 8.1 BOTS 负责什么
1. BOTS 是智能体开发平台，偏供给侧。
2. BOTS 负责定义智能体能力与属性。
3. 与能力强相关的业务属性优先放在 BOTS，例如：
   - 智能体适用场景：住院、门诊、科研等。
   - 是否需要调用患者数据。
   - 可被调用的业务系统接口。
   - 智能体输入输出要求。
4. 这些属性类似智能体的“说明书”，跨应用平台时仍然成立。

### 8.2 Copilot 负责什么
1. Copilot 是智能体应用管理与使用平台，偏需求侧。
2. Copilot 负责管理智能体在医院组织和客户端中的组合、展示和调用。
3. 与应用形态相关的属性优先放在 Copilot，例如：
   - 是否在医生工作站侧边栏显示。
   - 显示顺序、入口样式、触发条件。
   - 是否启用或停用某个科室、某类病历类型。
   - 是否安装到本机构或所有子机构。
4. 这些属性根据医院或科室部署要求灵活调整。

### 8.3 PRD 判断规则
1. 如果需求描述的是“这个智能体具备什么能力、需要什么输入、能输出什么内容”，优先写在 BOTS 或具体智能体应用章节。
2. 如果需求描述的是“这个智能体在哪里展示、给谁用、何时触发、如何安装、如何停用”，优先写在 Copilot 应用管理或 Common 公共能力章节，不应写成 Qt 客户端底座改造。
3. 如果需求描述的是“多个智能体共用的登录、首页、会话历史、智能体广场、智能体切换、患者关联、问答展示、流式输出、推理过程展示等能力”，按 Common 公共能力影响面说明。
4. 如果需求描述的是“Qt 客户端包、浏览器容器、消息桥接、接口转发、本地能力调用、窗口外壳”，才归入 Copilot 底座。

## 9. 患者关联、诊疗模式与通用模式
### 9.1 模式定义
1. Copilot 支持通用模式与诊疗模式。
2. 通用模式：不关联患者信息到对话上下文。
3. 诊疗模式：关联患者后，在请求内容中补充患者信息并传入模型。

### 9.2 患者关联入口
1. Copilot 界面提供患者列表按钮。
2. 点击后打开患者列表弹窗，展示当前登录人所在科室或病区的患者卡片。
3. 选择患者后，Copilot 进入诊疗模式，并在对话输入框上方展示当前关联患者卡片。
4. 用户可切换关联患者，也可关闭诊疗模式，断开患者关联并回到通用模式。

### 9.3 门诊与住院患者字段
1. 门诊患者列表字段：门诊号、序号、姓名、性别、年龄、接诊时间。
2. 住院患者列表字段：住院号、床号、姓名、性别、年龄、入院时间或出院时间。
3. 患者绑定卡片基础字段：姓名、年龄、性别、住院床号或门诊序号。

### 9.4 患者关联适用边界
1. 不是所有能力都支持患者绑定。
2. 工具型智能体一般没有业务属性，也不会存在关联患者逻辑。
3. 智能体应用是否支持患者绑定，取决于智能体功能配置。
4. 只有当智能体应用需要患者信息，且用户已关联患者信息时，患者信息才会被传入上下文。
5. 典型不需要患者关联的应用：科研问答、文献解析。
6. 典型需要患者关联的应用：病历生成、出院小结生成等。

## 10. 病历生成智能体与 Copilot 公共能力的关系
### 10.1 产品定位
1. 病历智能生成是大医医助系列产品中的应用模块型产品。
2. 它基于大医医助 Copilot 应用平台建设，聚焦医生文书工作场景。
3. 目标是提供结构化、可控、高质量的病历生成能力，帮助医生高效完成临床记录编写。

### 10.2 与 Common 公共能力的依赖关系
1. 病历生成依赖 Copilot Common 提供的患者关联机制。
2. 病历生成依赖患者数据获取能力。
3. 病历生成依赖病历类型、病历段落、段落书写规范、质控要求、段落依赖关系、段落数据需求等配置。
4. 病历类型可关联 BOTS 生成器；多个病历类型可选择同一个生成器。

### 10.3 患者数据来源
1. 病历生成涉及的数据来源包括 HIS、EMR、LIS、RIS、手麻系统、护理系统等。
2. 常见数据域包括：
   - 基础信息：患者主信息。
   - 就诊信息：就诊总表、门诊就诊记录、住院就诊记录。
   - 诊断信息：诊断记录。
   - 医嘱信息：门急诊医嘱、住院医嘱。
   - 检查信息：检查记录、病理报告。
   - 检验信息：检验结果。
   - 手麻信息：手术麻醉记录。
   - 病历信息：入院记录、住院病历文书记录、门急诊病历。
   - 护理信息：生命体征、护理文书记录、护理记录明细。
3. PRD 不应只写“调用患者数据”，必须写清楚数据域、必填/选填、完整性校验、缺失后的生成策略。

### 10.4 出院小结生成边界
1. 未关联患者时，不能使用病历生成智能体，应引导用户关联患者。
2. 出院小结按段落分别生成。
3. 整体视图没有对话框，不能在全文预览界面修改某一段落。
4. 对话生成和划词功能仅在段落内容修改界面生效。
5. AI 划词改写提供替换和插入，不生成新版本。
6. 段落整体 AI 对话生成每次请求会生成一个新版本，最多 5 个，队列式替换。
7. 病历生成智能体的历史不保留在普通会话历史中，如需查看，应通过关联患者进入病历生成智能体内查看。

## 11. 后续需求模块必须说明的影响面
### 11.1 必填判断
1. 模块归属层级：Qt 客户端底座、Common 公共能力、工具型智能体、助理型智能体、问答型智能体、后台管理或其他。
2. 模块是否影响患者关联、通用模式或诊疗模式。
3. 模块是否影响 BOTS 发布、Copilot 安装、机构权限或应用广场展示。
4. 模块是否影响已有工具型智能体、问答型智能体、助理型智能体或其他既有能力。
5. 模块是否改变本文档中的产品基线定义；如果改变，必须写清楚变更点、原因和影响范围。

### 11.2 推荐写法
1. 推荐在每个需求模块的“位置、目标”之后，用 4-6 行写清楚上下文与影响面，不建议在每个子需求下重复引用。
2. 如果模块影响面很小，使用“模块上下文说明”即可，不需要额外表格。
3. 只有当模块同时影响多个层级、多个应用或多个权限链路时，才补充影响面表格。

## 12. 给代码生成 AI 的使用规则
1. 在阅读某个迭代 PRD 前，先阅读本文档，理解产品背景和边界。
2. 生成代码时，以当期 PRD 的明确需求范围为准，不要因为本文档出现某项背景能力就主动改动相关代码。
3. 当期 PRD 未明确要求修改的 Qt 客户端底座、Common 公共能力、患者关联、BOTS 发布、Copilot 安装、会话历史、工具型智能体等模块，默认不改。
4. 当期 PRD 如只描述某个智能体应用，不得自动修改其他智能体。
5. 当期 PRD 如只描述 Qt 客户端底座，不得自动改写 Common 页面业务或智能体生成逻辑。
6. 当期 PRD 如只描述智能体生成逻辑，不得自动改动机构、权限、安装、发布流程。
